# Lecture M16 — Capstone framing

## The mental model

The capstone is one **Tenant Yoke** that exercises every
primitive you've touched. By design, the prompt is
deliberately open — the value is in the integration, not
in solving any single primitive in isolation.

## Key concepts

- **Integration over isolation.** A capstone Yoke that
  uses every primitive in isolation but doesn't glue
  them together fails the rubric. The point is the seams.
- **Rubric categories.** Schema authoring (M3, M5),
  authoring surfaces (M4, M7), runtime correctness (M6,
  M11), distribution (M10), and operations (M15). The
  rubric on [the capstone doc](/docs/training/capstone)
  expands each.
- **Reviewable by a second learner.** A capstone is done
  when a second learner can install it on a fresh tenant
  and follow the documented walkthrough end-to-end. This
  is the real exit criterion.
- **No starter code.** Intentional. Reaching for a
  template short-circuits the integration work — the
  rubric reads the integration, not the surface polish.

## Common pitfalls

- **Scoping too big.** The rubric doesn't reward feature
  count. A small, well-integrated Yoke beats a sprawling
  one with seams that don't connect.
- **Skipping the documentation pass.** "A second learner
  can install it" is a real test. Write the install
  walkthrough; have someone read it cold.
- **Treating the capstone as a portfolio piece.** It is
  — but the rubric scores integration, not presentation.
  Spend on the wiring, not the README.
